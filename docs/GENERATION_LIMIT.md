# Daily generation allowance

Each authenticated account has **3 generation attempts per UTC calendar day**, shared across solo and multiplayer games. The database clock determines the date; the allowance resets at 00:00 UTC (05:30 India time). A valid request is charged immediately before AI generation. Failures, cancelled requests, and timeouts after admission still count because they can incur provider costs. Invalid or unauthenticated requests do not count. Retrying setup for a saved multiplayer game makes no generation call and uses no additional allowance. This rollout starts with empty counters; earlier generations are not backfilled.

Apply `supabase/migrations/20261103151334_daily_generation_limit.sql` to every app environment before deploying the corresponding API. It creates an RLS-enabled counter table and a SECURITY INVOKER RPC. Only `service_role` can use the counter/RPC; the API passes the ID returned by Supabase `getUser()`, never a client-supplied account ID or date. An atomic conditional upsert admits at most three requests, including across concurrent requests and serverless instances. Missing or failed quota storage returns 503 before AI runs. Exhaustion returns 429 with an actionable message, `resetsAt`, and `Retry-After`.

Run `node --test tests/generation-limit.test.cjs` for endpoint admission checks. The opt-in `node --env-file=.env tests/generation-limit-smoke.cjs` verifies concurrent reservations and privilege restrictions against Supabase with disposable accounts and no paid AI calls. Add `--http` with the rebuilt app running at `127.0.0.1:3000` to verify the live API rejects an exhausted fixture with 429. Fixture deletion cascades its counters. See [the security remediation notes](SECURITY_REMEDIATION.md) for the publishing, dependency, and SVG fixes. This per-account allowance is not a global spending cap or protection against multiple-account abuse.
